# YuanbaoTalk 服务器规格

状态：v0.2 评审草案，2026-10-03。共同约定见 [协议规格](YuanbaoTalk-protocol-spec.md)。

## 1. 职责与边界

服务器按业务频道转发多条独立语音流，接收端混音；服务器不混音、不转码、不生成代替原始发言人的音频。数字和 UUID 频道同等支持，UUID 的线下交换不属于服务器职责。

每台设备都能自动成为网关，不能假设一个无线网络只有一个上行连接。服务器按原始消息身份去重，不能按网关连接身份识别语音源。

首版不要求加密，不把 UUID 当成加密或可靠身份认证。建议媒体和控制使用独立 WebSocket 连接；受控测试可使用 ws，wss 可作为部署选项。若使用 ws，频道、语音和接入令牌均可能被链路观察者获取，产品不能标称私密通话。

建议单个逻辑服务器。多进程时同频道归属一个所有者，注册、去重、计数和扇出决定原子执行；首版不定义跨服务器联邦。

## 2. 连接和订阅

设备主动连接。流程为 HELLO → WELCOME → JOIN → JOIN_OK → 媒体 BIND → READY，具体字段见共同协议。每控制会话首版订阅一个频道，媒体只能绑定本会话。

JOIN_OK 返回统一音频 profile、服务器并发流上限、目标无线段 TTL 和媒体绑定令牌。数字频道和 UUID 频道均不因知道频道号就获得无限服务器资源；设置连接、频道和设备/IP 配额。接入凭证为可选部署控制，不替代未来的音频加密。

网关允许代理自己和同频道无线源。首版无终端签名，服务器只能将声明的原始身份绑定到当前代理记录，无法证明无线源身份真实；该信任限制不能通过改称“认证设备”来掩盖。

## 3. 并发流注册

本地发言立即开始，不请求独占话权。网关通过 STREAM_OPEN 注册原始流，收到 STREAM_OK 后仅上传后续新媒体。未及时注册的前几帧可以丢失，不缓存整段等待许可。

建议服务器每频道最多 8 条活动源流；接收设备按自动或手动配置的有效容量 N 稳定选择混音流。8 是服务器容量建议，N 是设备性能预算，两者独立。已存在的同一流由多个网关注册时返回同一流句柄，不多占名额。容量满返回 STREAM_LIMIT；拒绝影响公网转发，不阻止源设备离线发言。

HELLO 与 CAPABILITIES_UPDATE 报告设备混音能力和当前有效路数。服务器不得因为网关只混音 N 路，就仅向它转发 N 路：网关后面的无线设备可能需要其他源。首版仍扇出频道内全部已准入流，设备本地选流；减少网络流量需另行设计带覆盖信息的订阅协议。

流键为 `(channel_id, origin_id, boot_id, stream_id)`。服务器记录已登记的代理会话、音频配置和最近新 AUDIO 时间。仅代理登记成功且配置匹配的连接可上传。某个网关断开只移除该代理；其他代理仍能上传。最后一个代理断开时停止转发并释放活动名额，但保留近期去重记录。

连续 1 秒没有新的有效 AUDIO 时结束该服务器活动流并释放容量；控制 STREAM_KEEP 可维持注册等待但不能让无音频流长期占名额。首版禁用 DTX，音频正常产生时每 20 ms 一帧。显式 END 记录最终采样位置，进入最多 300 ms 的收尾状态，仅接受未超期且采样位置早于终点的尾帧；随后释放名额并保存结束墓碑，不能因为 END 先到而直接丢掉全部尾帧。

断网恢复可用相同原始流重新注册，但只接收仍实时产生的新包；显式结束的流不可复活。服务器重启更换 server_epoch，所有句柄/媒体绑定失效，网关重新注册当前活动流。

## 4. 转发流水线

1. 检查会话、订阅、绑定、包长、速率和代理流句柄。
2. 检查协议/profile、字段、时间新鲜度，拒绝 via_server=1 的上传。
3. 以原始消息键做滑动窗口去重；无效包不更新窗口。
4. 保留源身份、流、序号、时间和编码字节，置 via_server=1，配置目标无线段 TTL。
5. 向同频道其他 READY 会话各投递一次，可排除本次入站会话；排除自身源的终端仍可作为网关为其他无线节点转发。
6. 下行携带服务器生成的流描述/注册事件，接收端无需等待最初 START 即可播放中途加入的流。

一个网关不得为同一频道创建多条活动媒体连接；重新绑定使旧连接失效。慢连接使用独立队列，不能阻塞频道其他订阅者。

## 5. 超时、背压和资源

- 控制心跳每 10 秒，30 秒失联关闭。单流媒体超时独立处理。
- 每订阅者媒体应用队列上限 100 ms，溢出丢最旧音频。TCP 已发送数据无法撤回；媒体持续阻塞 500 ms 时关闭并重绑，恢复不重放旧队列。
- 接收端也按采样时钟和公共时间映射判断陈旧，不能仅靠服务器丢包避免 TCP 延迟音频。
- 重连建议 1/2/4/8/16/30 秒退避加抖动；控制重连后重新 JOIN、BIND 和注册。
- 初始媒体限额每代理流 75 包/秒、突发 10 包；控制每会话 20 请求/秒、突发 20。实际接入上限还需考虑同一帧被多个网关上传的放大倍数。
- 连接数、频道数、流数、近期去重状态和扇出带宽均有部署上限，无容量返回 CAPACITY，不无限扩缓存。
- 指标包括原始流数、代理数、去重命中、陈旧/超限包、混音能力反馈、队列丢弃和扇出带宽；默认不存音频，不记录完整 UUID、令牌。

## 6. 传输取舍

WebSocket 便于首版实现，但 TCP 丢包会阻塞后续音频。它不是确定低延迟承诺；若目标弱网测试不合格，再冻结 UDP 的会话绑定、路径验证、乱序和限流规格。不要同时做两套含糊的首版媒体协议。

容量估算与场景验收见共同协议。硬件与网络规模未定，不宣称当前建议支持任意数量设备或任意跳数。
